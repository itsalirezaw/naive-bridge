# اتصال NaiveBridge به پنل ایران

کاربران و ورودی‌هایشان روی پنل ایران می‌مانند. پنل، ترافیک انتخاب‌شده را به SOCKS محلی NaiveBridge می‌فرستد. نصب پنل روی خارج یا انتقال کاربران به خارج لازم نیست. تنظیمات را ابتدا با یک ورودی آزمایشی بررسی کنید.

## 3x-ui

۱. از تنظیمات Xray و دیتابیس پنل پشتیبان بگیرید. روی ایران، `naive-bridge doctor` را اجرا کنید. سه مسیر باید موفق باشند.

۲. در تنظیمات Xray پنل، بخش **Outbounds / خروجی‌ها**، یک خروجی SOCKS بسازید:

- Tag: `naive-bridge-auto`
- Protocol: `socks`
- Address: `127.0.0.1`
- Port: مقدار واقعی خروجی **گزینهٔ 4** یا `naive-bridge panel`؛ مقدار پیش‌فرض `20080` است، اما اگر اشغال باشد پورت دیگری خودکار انتخاب می‌شود.
- نام کاربری و گذرواژه: خالی؛ این listener فقط محلی است.
- TLS، Transport و Mux اضافی: تنظیم نکنید. اتصال پنل به SOCKS محلی است و انتقال HTTPS را NaiveBridge انجام می‌دهد.

اگر از ویرایشگر JSON استفاده می‌کنید، **شیء** تولیدشده با `naive-bridge panel` را به آرایهٔ موجود `outbounds` اضافه کنید. نمونهٔ زیر فقط برای نصبی است که پورت انتخابی آن `20080` باشد؛ پورت واقعی نصب خود را جایگزین کنید:

```json
{
  "tag": "naive-bridge-auto",
  "protocol": "socks",
  "settings": {
    "servers": [{"address": "127.0.0.1", "port": 20080}]
  }
}
```

فرمان `naive-bridge panel` کل فهرست آماده را نشان می‌دهد. اگر پنل ویرایشگر یک outbound دارد، فقط شیء مربوط به همان outbound را وارد کنید، نه پوشش `{"outbounds": [...]}`.

۳. یک inbound آزمایشی و یک کاربر با حجم محدود بسازید. **تگ واقعی inbound** را از پیکربندی Xray بردارید؛ عنوان نمایشی یا Remark لزوماً تگ نیست.

۴. در **Routing Rules / قوانین مسیریابی**، بعد از قوانین ضروری API و مسدودسازی، و قبل از قانون عمومی‌ای که ورودی آزمایشی را می‌گیرد، قانون زیر را اضافه کنید:

```json
{
  "type": "field",
  "inboundTag": ["YOUR_TEST_INBOUND_TAG"],
  "outboundTag": "naive-bridge-auto"
}
```

به‌جای `YOUR_TEST_INBOUND_TAG` تگ واقعی را قرار دهید. قانون API، محدودیت دسترسی به شبکه‌های خصوصی و قوانین دیگر خود را حفظ کنید. Xray قوانین را به ترتیب بررسی می‌کند؛ قانون عمومی زودتر می‌تواند مانع رسیدن به این قانون شود.

۵. تنظیمات را با اعتبارسنجی پنل ذخیره و Xray پنل را restart کنید. با کلاینت همان کاربر به **سرور ایران** متصل شوید. بازشدن سایت، دانلود و آپلود، IP خروجی خارج و افزایش مصرف همان کاربر را بررسی کنید. اگر IPv6 در خارج فعال باشد، برخی مقصدها IPv6 خارج را می‌بینند.

این روش SOCKS در آزمون نمونه با **3x-ui 3.8.5** برای TCP، UDP و ثبت مصرف بررسی شد. عنوان و محل گزینه‌ها در نسخه‌های دیگر پنل ممکن است متفاوت باشد.

## تخصیص کاربران به نود مشخص

خروجی `naive-bridge panel` برای هر نود یک تگ مانند `naive-bridge-fi1` می‌دهد. پورت همهٔ نودها خودکار انتخاب و ذخیره می‌شود؛ مقدار واقعی فرمان را استفاده کنید و پورت‌ها را حدس نزنید. پورت SOCKS ایران مستقل از پورت HTTPS خارج است و فقط روی `127.0.0.1` استفاده می‌شود.

برای انتخاب همان نود، در قانون بالا `outboundTag` را به تگ آن نود تغییر دهید. خروجی ثابت، هنگام خرابی به کشور یا نود دیگری نمی‌رود؛ داخل همان نود از Naive به XHTTP تغییر می‌کند. برای عبور خودکار به نود بعدی از `naive-bridge-auto` استفاده کنید.

برای شروع، تخصیص بر اساس inbound روشن‌تر است. اگر بر اساس کاربر مسیریابی می‌کنید، از فیلد `user` و شناسهٔ email واقعی‌ای که پنل به Xray می‌دهد استفاده کنید؛ نام نمایشی پنل را به‌جای آن ننویسید.

## DNS و UDP

UDP از SOCKS5 محلی به XHTTP می‌رود. Naive در این نسخه حامل UDP نیست؛ برای DNS و برنامه‌های UDP، نتیجهٔ `udp` در `doctor` را بررسی کنید.

درخواست‌های DNS ارسالی **از داخل ترافیک کاربر** تابع قانون ورودی او هستند. DNS داخلی خود Xray پنل می‌تواند مسیر جدا داشته باشد. اگر پنل برای مسیریابی یا resolve از DNS داخلی استفاده می‌کند، صرف افزودن outbound باعث انتقال آن DNS نمی‌شود.

برای عبور DNS داخلی Xray از تانل، به تنظیم موجود `dns` یک تگ مانند `nb-dns` بدهید و قانون متناظر را بعد از API و قبل از قوانین عمومی اضافه کنید:

```json
{
  "type": "field",
  "inboundTag": ["nb-dns"],
  "outboundTag": "naive-bridge-auto"
}
```

نمونهٔ حداقلی بخش DNS، فقط برای ادغام با تنظیمات موجود:

```json
{
  "dns": {
    "tag": "nb-dns",
    "servers": ["1.1.1.1", "9.9.9.9"]
  }
}
```

این دو resolver از UDP قابل‌مسیریابی استفاده می‌کنند. گزینه‌های `localhost`، `https+local://` و `tcp+local://` عمداً از مسیر محلی resolve استفاده می‌کنند؛ برای ادعای عبور DNS از تانل آن‌ها را انتخاب نکنید. تنظیم سفارشی DNS کاربران و سیستم‌عامل مستقل است. [مستندات DNS در Xray](https://xtls.github.io/en/config/dns.html)

## پاسارگارد

در پیکربندی **هستهٔ Xray روی ایران**، همان outbound SOCKS و قانون Routing را اضافه کنید. ورودی و کاربر همچنان روی هستهٔ ایران باشند؛ قابلیت Node خود پنل برای این اتصال لازم نیست. NaiveBridge خروجی شبکه فراهم می‌کند و سامانهٔ Node داخلی پنل را جایگزین نمی‌کند.

منطق پیکربندی مطابق Xray است، اما نصب واقعی و رابط/API پاسارگارد در آزمون این پروژه بررسی نشده است. با یک کاربر آزمایشی، هم عبور داده و هم ثبت مصرف و اعمال محدودیت را در نسخهٔ خودتان بررسی کنید. اگر پنل تنظیمات را تولید می‌کند، تغییر را در template/config مدیریت‌شدهٔ پنل ثبت کنید تا با restart بازنویسی نشود. [پروژهٔ پاسارگارد](https://github.com/PasarGuard/panel)

## پنل Docker

`127.0.0.1` باید از دید **پردازش Xray پنل** همان میزبان NaiveBridge باشد. نصب مستقیم و Docker با `network_mode: host` این شرط را دارند. در شبکهٔ bridge داکر، loopback کانتینر جداست و این نمونه به‌صورت خودکار قابل‌استفاده نیست. قبل از تغییر شبکهٔ کانتینر، پورت‌های پنل و تداخلشان را بررسی کنید؛ بازکردن SOCKS روی اینترنت راه‌حل مناسبی نیست.

## سناریوی کوتاه ویدیو

نصب خارج، نمایش کد با پوشاندن بخش محرمانه، نصب ایران، سه نتیجهٔ موفق `doctor`، ساخت outbound، قانون یک ورودی آزمایشی، اتصال کاربر و نمایش IP خارج و افزایش مصرف پنل. سپس اضافه‌کردن نود دوم و تفاوت خروجی ثابت و خودکار را نشان دهید. رمزها، کد NB1 و لینک اشتراک کاربران در تصویر نباشند.
